Warum überhaupt

Agenten, die direkt losprogrammieren, kosten später Zeit

Ohne festen Prozess trifft ein Agent die gleichen Fehler wie ein ungeführtes Junior-Team — nur schneller.

1Anforderungen werden nicht hinterfragt — der Agent codiert die erste Interpretation.
2Tests entstehen (wenn überhaupt) nachträglich, als Bestätigung statt als Spezifikation.
3„Fertig" ist eine Behauptung des Agenten, kein nachgewiesener Zustand.
4Review und Abschluss passieren ad hoc, ohne wiederholbaren Prozess.
Das Konzept

Superpowers macht den Prozess explizit — und automatisch aktiv

115 zusammensetzbare Skills statt einer starren Anleitung — für Planung, Umsetzung, Qualität und Abschluss.
2Der Skill using-superpowers erkennt selbst, welcher Skill gerade gebraucht wird — niemand muss ihn manuell auswählen.
3Testgetrieben und evidenzbasiert: ein Fix gilt erst als erledigt, wenn er nachweislich wirkt.
4Plattformübergreifend nutzbar — u. a. mit Claude Code, Cursor, Devin und Gemini.
Im Original-Ton

Was im offiziellen README steht

„a complete software development methodology for your coding agents" — so beschreibt das Projekt sich selbst, direkt in der ersten Zeile.
1Der Agent fragt zuerst nach, was wirklich gebraucht wird, statt direkt loszucoden.
2Die Spezifikation wird in lesbaren Häppchen vorgelegt und muss freigegeben werden, bevor etwas gebaut wird.
3Der Plan muss so klar sein, dass ihn laut README „an enthusiastic junior engineer with poor taste" fehlerfrei umsetzen könnte — mit echtem Red/Green-TDD, YAGNI und DRY.
4Erst nach dem „go" startet der subagent-driven-development-Prozess — laut README nicht selten stundenlang autonom, ohne vom Plan abzuweichen.

Perspektive

Was ändert sich konkret — pro Rolle

Dev-Team

  • Klare, 2–5-minütige Tasks statt vager Tickets
  • TDD und Review-Gates sind eingebaut, nicht optional
  • Debugging folgt einem reproduzierbaren Prozess

Product Manager

  • Sichtbare Checkpoints, bevor Entwicklungszeit investiert wird
  • Fortschritt ist in kleinen, nachvollziehbaren Schritten sichtbar
  • Kein Merge ohne dokumentierten Qualitätsnachweis

Product Owner

  • Anforderungen werden vor der Umsetzung aktiv hinterfragt
  • Pläne sind auch ohne Code-Kenntnisse lesbar und prüfbar
  • Weniger Scope-Drift durch explizite Spezifikation

Testmanagement

  • Test-first ist Standard, nicht Nachgedanke
  • „Fertig" heißt: verifiziert, mit Nachweis — nicht behauptet
  • Fehleranalyse folgt einem festen Vier-Phasen-Schema

Ein Prozess, kein Zufallsprinzip

Superpowers ersetzt Hoffnung durch einen wiederholbaren, rollenübergreifend nachvollziehbaren Ablauf.
